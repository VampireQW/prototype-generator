# PRD 撰写规范

适用于页面需求与序号标注的新增、改写和重新整理；与 `prd-import.md` 的范围、确认保护和草稿协议一起使用。PRD 记录已确认的产品规则，要求严谨、确定、可核对。

风格整理保留业务含义、次数、阈值和历史日期，不借润色新增规则或替用户决定未知项；仅更新规范不等于已重写现有项目 PRD。

## 先确定范围、依据与承载位置

1. **先列本期业务清单**。从用户已确认的需求和决定出发，明确项目、适用端、页面与状态，以及新增、调整、移除、复用的部分。角色、学段、学科、地区、租户、版本或灰度条件确实影响开放结果时，写清开放对象、可见入口和未开放时的行为。多维条件有实际差异时用对照表，表里每行对应一组可判断的条件。
2. **范围按 `prd-import.md` 确认**。默认仅写本期改动及确实改变的联动。完整页面需求和整页点击提示各自确认，范围限定到已选页面、状态和业务项。选择完整页面需求时，写清清单内已核实的现行业务，分别标明沿用项和本期改动。已经确认的清单直接沿用，扩项只确认新增部分。仅整理 PRD 时保留原点击提示。确有存量影响时，一并确认历史数据策略。落库时遵守已有确认保护、人工删除保护和点名清理约定。
3. **背景写问题，目标写结果**。背景说明谁在什么场景遇到什么问题。目标说明本期完成后用户能做成什么或改善什么。两者可按需省略。按钮文案、校验、配额、显示和跳转规则写在标注中。有量化目标时使用已确认的口径和数值。
4. **证据和决定分开**。当前用户确认、已核实的旧行为、原型示意和历史参考各有用途。正文写已确认的本期规则，旧行为用来比对变化，原型和截图用于定位与演示。图文冲突、历史版本互相矛盾或关键分支无依据时，列出差异及其影响，向用户确认会改变结果的决定，待确认内容进入 `unknowns`。记录真实需求原文及改造前后，沿用现有 `sourceQuote`、`before`、`after` 和 `requirementId`，不得借相同需求编号带入无关规则。
5. **按序号组织业务内容**。页面需求只承载本期背景和目标。序号按一个可独立讲清的功能或业务区域聚合，依附可定位的元素。每条标注按业务顺序用列表展开。涉及多个页面时分别写清实际变化和联动结果，流程图或原型作为参考。落库仍逐条关联需求，条目顺序与阅读顺序一致。

## 规则表述

- 直接写清适用对象、触发条件、状态与结果。次数、范围、默认选中、边界和扣减时机，以已确认内容为准；没有依据的部分放入草稿 `unknowns`，不补成正式结论。
- 删除口语、讨论经过、评审感受、重复背景和空泛解释。不得用“建议、尽量、适当、大概、应该、同上、同理”等代替具体规则；避免“更友好、避免用户感觉……、本状态同样处理”等无可核对内容。确有依赖时明确写出条件和结果，不让读者跨标注猜规则。
- 产品界面上的原文逐字保留。界面文案本身含“建议、参考”等词时，不因措辞规则擅自改写。用户提出但尚未确定的建议，与正式产品规则分开。
- 原型演示的假数据、写死时长和模拟成功不等于实际系统规则；例如原型用定时器模拟完成，不能据此写“1.6 秒后全部成功”。只保留已确认的业务反馈与完成条件。

## 序号标注的列表写法

正文使用有序或无序列表。流程有先后关系时用有序列表，并列规则用无序列表。主项讲清一个业务点，相关条件、动作和反馈可以写成缩进子项。按阅读顺序组织以下内容，无需为每项都设置固定栏目。

- **主要显示元素**。可用“页面显示”作为列表项内的短标签。列出本期相关的主要区域、入口、字段、列表列项和状态提示，写清必要的可见条件。
- **实际状态及其操作**。有默认态、进行态、完成态等差异时，按实际状态分条。说明进入条件、显示变化、可执行操作及状态转换。各状态下实际存在的点击、悬浮等操作及反馈写在对应条目内。
- **动作、反馈与业务结果**。在同一处交代触发动作、适用条件和结果。弹窗写清确认与取消的后果，跳转写清去向和必要的落点，提示写清何时出现及文案。保存、扣减、状态转换、数据联动等规则跟在触发它们的动作下。跨多个状态的共用规则可单列一次。
- **补充情况**。分页、排序、空状态、失败重试等写在相应列表、状态或操作之后。只写本期相关的分支，统一使用列表项和子项表达。标注正文省略按固定类别重复出现的 Markdown 大标题。

## 按本期涉及的场景补齐规则

| 场景 | 需要交代的规则 |
| --- | --- |
| 开放、角色与权限 | 区分是否开放、是否看得到、是否能操作。写明谁可对什么对象执行什么动作，以及本人和他人资源、组织范围、当前状态的差异。入口隐藏、置灰、允许点击后提示和拒绝直接访问各有不同结果，按已确认的行为写。 |
| 表单、选择与校验 | 明确可选范围、首次与再次进入的默认值、单选或多选、必填、允许值和限额。说明上游选择变化时，下游已选项如何保留、重置或重新校验。校验失败写触发时机、提示位置和提交结果。 |
| 列表、检索与筛选 | 明确数据来源和纳入范围、默认条件、搜索与筛选的组合、数量统计口径。分页、排序、加载和空结果按下节补齐。 |
| 多步骤流程与状态 | 写明从哪个入口进入、初始状态、允许操作、状态转换条件和完成后的落点。按实际情况交代返回、取消、关闭、刷新或再次进入时，已填写内容、已选对象与进行中任务如何处理。多个入口有差异时单列。 |
| 异步、失败与恢复 | 涉及上传、转换、生成、同步等过程时，分别描述进行中、成功、失败及必要的取消、重试和恢复。说明重复触发是否会重复创建或扣减，失败是否已经产生可见记录、是否保留输入或旧结果，以及用户下一步可做什么。只记录已确认的行为。 |
| 关联、共享与跨端联动 | 写清业务数据来自哪一处、哪一步形成记录、何时对谁可见、哪些内容同步、复制还是引用，以及后续编辑、撤回、删除是否联动。分别列出实际受影响的页面、列表、端或下游。原型上没有新增控件的数据变化也要有规则落点。 |
| 历史业务数据 | 涉及旧记录时，写清新旧分界、旧值及缺失值的含义、读旧数据时的处理、是否补齐或重算、是否影响既有结果与统计。缺乏可靠映射时交由用户决定。处理策略与真实迁移操作的授权分开。 |
| 计算、报表与诊断 | 明确指标定义、统计对象与粒度、纳入和排除条件、时间范围、计算公式或分子与分母、去重和显示精度。说明状态与筛选改变时如何更新。核对缺值、分母为零和阈值相等时的结果，只有现有依据无法确定且会改变结果时才询问。用示例数核对公式、展示值和解释文案。 |
| 文件与导入导出 | 若本期涉及，列出允许的格式、数量或容量、文件名规则、导出对象范围，以及处理中、失败、取消与重新提交的结果。格式和容量是业务约束，按已确认值写。 |

## 分页、排序与空状态

本期新增或改造列表时，逐项核对分页、排序和结果状态。详情、报表等其他数据区域可能为空时，也写明对应的展示与操作。具体规则放在相关数据区域或操作的条目下。

### 分页与加载

- **先定方式和条数**。明确不分页、页码分页或滚动分页。常规页码分页以**每页 10 条**为默认，已有明确规则的页面沿用已确认的条数。采用滚动分页或其他条数时，按数据量、端和使用场景确定，并写清每次加载多少条。
- **写清分页边界**。页码分页说明默认页、末页不足一页的展示，以及搜索、筛选、排序或刷新后回到哪一页。删除或数据变化使当前页无记录时，明确页码是否回退和回退到哪一页。
- **滚动分页单独写加载规则**。明确首批和后续每批条数、加载触发条件、加载中反馈、数据加载完毕后的表现。继续加载失败时，写清已加载记录如何处理，以及从哪一批重试。

### 排序与异常

- **说明依据和范围**。写清默认排序字段的业务含义及方向。例如使用“更新时间从新到旧”。支持切换排序时，列出可选项、切换方式和生效范围。涉及分页时，明确排序作用于整个筛选结果还是当前页。
- **补齐边界**。排序值相同且跨页顺序受影响时，明确次级排序依据。可能出现空值时，明确空值如何排列。新增、删除或更新使记录位置变化时，说明当前页和已加载列表如何更新。仅对实际会出现的情况写规则，依据不足的结果进入待确认项。

### 空状态与失败状态

- **区分出现条件**。至少核对该区域可能出现的无业务数据、搜索或筛选无结果、数据加载中和加载失败。若存在权限或开放范围导致的不可见，按对应权限规则写明。
- **说明展示和下一步**。每个实际存在的空状态写明出现条件、用户看到的内容及可执行操作。无业务数据时，按需求说明是否给出创建、导入等入口。无筛选结果时，说明是否保留筛选、如何调整或清除。加载失败时，说明提示、重试及已有结果是否保留。
- **说明页面其余部分如何呈现**。按实际情况写明表头、筛选区、分页区和操作入口的保留或隐藏。首次加载成功但为空、末页数据被删空、筛选结果为空和追加加载失败分别核对。

## 表达复杂业务及其验证条件

- **把分支写在相关条目下**。同一需求下，角色或状态不同会改变可见内容与操作时，按“适用对象或前置条件 → 触发动作 → 状态或结果”组织子项。先写共同规则，再列例外。存在交叉条件时明确优先级或组合方式。确有多维对照时，可在相关条目附简洁状态表辅助核对。
- **跨页流程先写主线，再补断点**。主线列起点、关键节点、到达状态。取消、返回、权限不满足、状态失效等分支补在它们出现的位置。流程图可辅助理解，正文仍提供关键条件、结果与回退去向。复用旧逻辑时，只说明本期必要的复用对象及一致的关键行为，单列变化点。避免“同上”或“沿用原逻辑”成为唯一说明。
- **统计口径与埋点分开核对**。前者是产品显示与计算规则。只有本期确有埋点交付要求时，才记录事件目的、触发时机、统计对象、成功判定、去重及待核对的口径。实际事件名和技术参数放到有依据的独立约定。历史 PRD 的“打点待补充”仅表示旧项目未决。
- **用可观察的结果判断规则完整性**。对本期关键规则检查在给定对象、数据和状态后，执行动作是否能得出唯一预期。优先核对首次和再次进入、上下限等号、成功与失败、取消或刷新、旧记录与新记录。只检查实际相关的边界，尚未明确的结果继续待确认。验收条件可复用规则条目，避免重复抄一份正文。

## 分条与换行

- 一个顶层条目只写一个可独立核对的业务点。相关的显示条件、默认值、校验和反馈可分成子项。
- 按草稿的 `items` 逐条写，每项关联同一或对应的 `requirementId`。每项承载一个顶层列表项，必要的分支放在它下面。保持原标注的业务归属，不因分条就新建多个序号。
- 用独立列表项和缩进表示层次。落库后核对阅读态的编号、缩进和顺序，确认规则没有被拆散、挪序或挤成一段。

## 引号与重点

| 内容 | 写法 |
| --- | --- |
| 按钮、可操作入口 | 点击「重批」、点击「取消」 |
| 标题、字段标签、状态名称、提示及其他界面文案 | 弹窗标题为“重批”；显示“智批进行中” |
| Toast / 气泡 / 错误提示的具体文字 | 提示“重批次数已用完” |
| 按钮上的动态数字与额度 | 「重批」按钮；剩余次数为 0；不要把说明混进按钮名称 |

正文统一使用中文标点，不混用 `【】`、方括号和英文引号标记同类界面元素。同一文字作为按钮名称时用「」，作为标题或提示内容时用“”。技术协议与 JSON 结构的语法引号不在此范围。

关键限制、例外、不可逆后果、额度扣减和边界可用 **加粗** 或少量标红，强调具体规则片段；普通描述不通段加粗、标红。产品自身的红色提示与 PRD 重点标记含义不同，不能因为标红就写成界面必须显示红色。

## 更新记录

- 统一写 `（YYYY-MM-DD 更新：具体变化）`，不用“拍板、定稿、起不再……”等会话式记录。写明实际更新了什么，不只写“已更新”或模糊的“扩展”。
- 日期以实际需求更新依据为准，旧记录改措辞不改原日期，不把本次整理时间冒充需求变更时间。当前有效规则放正文，简短括注紧跟受影响条目；无需逐条重复无意义的更新时间。
- **更新括注从左括号到右括号整段统一标红，包含日期、“更新”及变化说明。** 使用工作台支持的内联文字颜色，不能只给某个词标红，也不能把颜色语法放进代码块导致读者看到源码。
- 写法示例：`<span style="color:#ec4954">（2026-11-04 更新：补充次数用尽时的按钮反馈）</span>`。这里的颜色值是 Markdown 文字格式的内部表示，不是 PRD 展示给研发的业务内容。

- 有文档历史、正文标注和评审评论并存时，核实哪条已确认生效，正文保留当前有效的规则。历史版本、延期项或撤销项用于说明本期边界和追溯变化。多处引用同一规则时，以明确的现行条目为准，其他地方只补本期差异。无法确定生效日期或优先级时记录待确认，不补造日期。

## 产品规则与实现边界

- **PRD 只描述业务逻辑、显示条件、必要的位置关系和交互结果，不约定视觉参数。** 不写像素尺寸、宽高、间距、留白、字号、圆角或位置坐标等设计数值，也不从原型 CSS 中提取这些约定；不能把 `268px` 改写成“268 像素”或换用其他尺寸单位继续写入。具体视觉由 UI 与研发确定。
- 将尺寸实现转成已确认的行为。例如“目录卡片宽 268px，距顶部 24px，最高为工作区高度减 48px”，改成“目录卡片悬浮显示在工作区左侧，高度随目录数量自适应；目录内容超出工作区可用高度时，在卡片内滚动”。保留定位、显隐、收起展开和滚动规则，不凭空增加视觉效果。
- 业务次数、额度、数量、时间范围和阈值仍按已确认内容保留，不因移除视觉数值而删除业务约束。
- PRD 正文用业务语言描述可见效果，如“按钮置灰、保留显示、不可提交、鼠标移入时显示禁用样式”。不写十六进制 / RGB 色值、CSS 属性（如 `cursor:not-allowed`）、选择器、DOM 标记、组件名或原型内的代码变量。
- 不从原型脚本推断真实系统字段、接口、参数、数据库表名或枚举。未核实的实现映射不写；实际系统命名不明确时，使用“剩余重批次数、批改状态”等业务名称，不虚构对应技术名称。
- 用户明确提供并要求记录的真实技术契约，放到独立的接口 / 技术约定中并标明依据，不混入产品规则；未知项继续待确认，不能把原型变量冒充契约。
- 草稿 / 锚点中的 `protoId`、`selector`、`requirementId` 等是工作台定位与追溯元数据，仍按协议保留，不展示为真实系统字段。锚点坐标、图片排版宽度和文字颜色等内部格式元数据按协议保留，不将其转写成产品视觉约定。

## 交付前逐项复核

- **范围**。每条内容是否在已确认清单内，能否找到依据并解释本期发生的变化。原型截图、实现代码、旧文档和评论不能代替本期授权。页面规则是否放在对应标注，背景和目标是否夹带控件细节。
- **条件**。对真实涉及的角色、默认值、状态、权限、阈值、时间与范围，逐项检查等号、空值、冲突和缺数据时是否会产生不同理解。动态文案中的变量以业务含义说明。需求只规定置灰外观时，再核对是否仍响应点击以及响应结果，避免把视觉表现误作可操作性。
- **结果**。用一条主要路径和本次最可能出错的分支反查，检查取消后是否保存、失败后是否产生记录、刷新后是否恢复、跨端是否显示同一口径。涉及统计的，用能跨过边界的一组小样例核对计算和提示。
- **列表边界**。涉及列表时，用 0 条、刚好一页和多 1 条核对分页与空状态。存在同值或空值时核对排序。再按本期场景检查筛选无结果、删除末页最后一条或加载下一批失败时的展示和操作。
- **文档与原型一致性**。正文应能独立读懂核心规则。若当前原型只模拟部分行为，区分已确认规则与演示能力。确认未决项、已知差异和本期排除项能被追溯。导入时继续使用现有校验与阅读态复核，工具的结构通过不能替代产品语义确认。
- **阅读顺序**。每个序号下连续阅读主要元素、状态、可用操作和反馈。确认操作与相应业务结果放在一起，正文使用列表与子项展示，分页、排序和空状态能从对应功能条目找到。
