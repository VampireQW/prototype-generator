# PRD 草稿与落库

## 落库前范围确认

读取本期用户需求、相关会话与项目 `.prototype/brief.md`，再读取实际改动和当前元数据，先形成简短的业务撰写清单。页面代码用于核对业务和定位，不自动授权把已存在的所有功能写入 PRD。

### 一次选择，确认具体内容

尚无用户已确认的具体清单时，在写正文及正式导入前，使用当前 Agent 可用的询问工具；没有选项工具则发送编号文本问题。三个选项同时给出，前两个都列出实际拟写的业务项，不只展示“全部 / 本次”标签：

| 选项 | 向用户展示什么 | 执行范围 |
| --- | --- | --- |
| 仅本次改动（推荐） | 本轮新增或改变的功能，以及必要且确实改变的联动 | 清单内的本期变化，使用 delta |
| 当前页面完整业务需求 | 选定页面 / 状态中已核实的业务功能，按功能归组 | 仅这些页面 / 状态的完整业务需求，使用 full |
| 自定义范围 | 支持按业务项编号选择、增删，或用文字 / 截图指定 | 按用户实际选择形成清单；原有功能也被明确纳入时使用 full，仍限定清单范围 |

问题同时说明项目、端、页面 / 状态、容易混入的排除项、背景 / 目标是否准备更新，以及点击提示准备保留 / 替换 / 清空及其具体控件。用业务名称表达，不要求用户看元素 ID、接口字段或完整 PRD。多页按页面分组，条目过多先归纳功能，不把每个按钮或表格单元格列成一个需求。

例如本轮只涉及“需讲解”开关，且已核实页面原有 Tab 和答题结果展示时，可以问：

> 项目：实际项目名；页面：作业详情（学生平板）／default。
>
> 1. **仅本次改动（推荐）**：按钮改为开关；开关状态与文案；切换后本轮实际改变的反馈。
> 2. **当前页面完整业务需求**：学案 / 作业切换；答题结果展示；需讲解开关。其他已核实业务项按实际页面补列。
> 3. **自定义范围**：回复需要保留、增加或排除的业务项，也可以截图框定。
>
> 选择 1 时不写原有 Tab 和答题结果展示；背景目标只按需写开关改造。仅整理 PRD 时保留已有点击提示；本轮还需更新交互提示时，只替换为开关相关控件。
>
> 请选择 1、2，或描述自定义范围。

以上仅示范问题结构，实际选项必须使用本次真实业务项，不照抄示例或补造状态、接口与联动。这里的“完整”仍按业务规则聚合标注，不代表页面每个元素都要一个序号，也不扩展到整个项目或其他端。选择完整 PRD 不自动授权整页点击提示。

### 哪些情况已经确认

- 用户已明确具体业务项、页面 / 状态，并要求按该范围落库；或已接受同一份具体清单：简述沿用范围后直接执行，不再询问。
- 用户只说“落库 / 按新标准重落库”，且没有可恢复的已确认具体清单：展示上述选项并等待答复。只有“本次改动”标签、没有具体业务项的选择，不能用于批准 Agent 尚未展示的扩展内容。
- 用户的编号或“按第一个”答复结合当时展示的选项解释，保留真实答复与清单的对应关系；不要把 Agent 的选项文案冒充用户逐字原文。
- 没有答复时保持等待，可以继续只读核对；不得自行选择推荐项、代填确认或正式导入。相同范围的后续保存不反复确认；扩入新的业务项、页面 / 状态，或扩大点击提示时，只询问变化部分。

确认后在 `.prototype/brief.md` 的本次 PRD 范围中简短记录项目 / 页面 / 状态、选项、包含项、排除项、点击提示操作与确认依据，保留历史事实。范围沿用仅限同一任务，不能把上一期确认套到新需求。`scope.request`、`sourceQuote` 和 fullRequest 等继续保留真实用户需求 / 选择原文，不伪造授权。

### 涉及历史数据时同时确认处理策略

这里的历史数据是原型所描述产品的已有业务记录，不是平台已有的 PRD、序号标注或导入历史；后者仍按确认保护、人工删除保护及点名清理协议处理。

对本次功能改造核对存量兼容性：新增字段在旧记录中的缺省含义、状态 / 枚举的旧新映射、计算 / 统计口径变化、分组 / 归属 / 关联方式变化等。只有确实涉及，或存在会改变处理结论的关键未知时才询问。纯布局、颜色、文案优化，或已有状态能同义复用的按钮改开关，不凭空增加迁移问题；无相关影响时直接继续。

需要确认时，和前文范围选择在同一轮展示；范围已经明确则只问历史处理，不重问范围。用用户能理解的业务名称简述：

- **影响**：哪类旧记录、哪个字段 / 状态 / 统计会受影响；已知的时间或处理状态边界。不编造记录数量、数据来源、旧字段或已具备的迁移能力。
- **处理选项**：给出当前证据支持的可行方案，例如“旧记录保留原含义、新记录采用新规则”“按可靠的旧字段映射补齐 / 重算”“按时间或记录状态自定义范围”。每项写清旧记录会怎样显示、是否改变既有结果及主要代价，不机械固定三个方案。
- **建议**：推荐一项并说明依据和取舍；证据不足时指出缺口，不把推测当事实。推荐不等于用户已选，未回复不能采用默认策略。

例如：本次新增“需讲解”标记，且已核实历史记录没有可用于判断学生意愿的字段。可以说明“无法从旧记录推断是否需要讲解”，建议“旧记录保留未设置状态并单列统计，新记录按新规则”；同时提供“旧记录统一赋指定值（会把未知意愿计入该值）”或“按用户指定条件处理”等实际可行选项。这里的建议、展示和统计方案都须用户确认后才能成为规则，不能把缺失值擅自当作“不需要”。若已有可靠旧字段可同义映射，应根据该证据调整建议，不能照抄此例。

用户选定后，只补齐与本期有关的处理边界：旧 / 新记录的区分条件、缺失值与旧状态的含义、兼容读取或补齐 / 重算方式、结果与统计口径。涉及覆盖既有结果、无法映射或失败时，再明确相应保护和恢复行为；无需为无关项凑内容。信息不足且会改变处理结果时继续问具体缺口，用户已有明确决定且条件未变则直接沿用。

把确认的处理项补入本次业务清单，在 `scope.requirements` 中追溯到用户真实需求 / 选择；按实际内容写入现有“页面显示 / 数据流转 / 业务规则 / 交互说明 / 异常情况”小节，不强制新增固定章节，也不要求五项齐全。brief 记录处理决定、适用范围和确认依据，不复制真实业务数据。未决策略放入 unknowns，依赖它的默认值、统计或迁移规则不落成定论；等待期间可继续不依赖该决定的准备工作，完成回复说明未决部分。

确认 PRD 中的处理规则只授权记录该产品决定，不授权 Agent 实际迁移、批量更新、重算、清空或修改业务库；执行真实数据处理须另有明确的执行授权。

### 按确认清单核对草稿

把清单逐项映射为 `scope.requirements`，为相关页面 / 状态列出 targets；背景、目标、每条标注及本轮新增或替换的热点都须对应已确认的业务项，涉及历史业务数据的处理规则也要有确认依据。已有热点选择 preserve 时保持原值，不把历史范围当成本轮新增授权。共享容器或 requirementId 不能作为夹带清单外旧规则的理由。

正式导入前将 dry-run 报告与清单对照，简述新增、更新、保留和拟删除项；清单内没有的提交内容先移除，确需扩项时再询问变化部分。已有 PRD 留在页面上不等于本轮新写入，报告中要区分；范围收窄不自动删除历史 PRD，清理误注按后文的点名删除协议处理。

当前工具校验结构、引用和定位，无法证明用户确认或判断业务语义；范围确认及逐条比对由 Agent 执行。不向版本 3 草稿添加自拟的 `confirmed: true` 作为用户确认凭据，也不宣称平台已有独立的范围审批闸门。元数据中的 confirmed 仍仅用于已有内容保护。

## 已选范围的内容判断

用户说“按新标准重新整理 / 重新落库”时，沿用已确认清单，不能解释为补全整页 PRD；本轮没有复述需求时，从同一任务的已确认上下文恢复，不拿整个项目介绍代替。

默认 `scope.mode: delta`。逐项列出本期变化，写清用户需求原文 `sourceQuote`、改造前 `before` 与改造后 `after`。`scope.request` 保留本期真实需求原文；sourceQuote 须能在其中找到，不能拿页面代码、旧 PRD 或 Agent 自己的功能总结伪装成用户需求。可用 `exclusions` 简短列出容易混入的既有功能。

采用 full 时按已确认的业务清单撰写，保留原有业务的事实属性，不把保持不变的功能伪写为本期变化。下列逐条检查仅适用于 delta，包括仅选择本次变化的自定义范围；对背景、目标及标注的**每一条**都要判断：

- 如果撤销本期改造，这条描述仍然原样成立，它通常是既有功能，删掉这条待提交内容。
- 只有本期新增、实际发生变化的显示 / 数据 / 规则 / 交互 / 异常，及解释这些变化不可缺少的联动才写入。必要联动要指出随本期实际改变了什么；同页、同容器、具有交互、代码被格式化都不是依据。
- 把“本期新增的开关”放在旧题卡里，不代表要描述整张题卡。保留理解新变化所必需的最短上下文，不为旧规则单独建条目、序号或点击提示。
- 不用“本期改造：……”一句话给整段旧功能说明兜底，也不以引用同一个需求 ID 的方式夹带无关业务。工具检查引用和结构，语义是否属于本期仍由 Agent 判断并复核。

例如本期只把“我不需讲解”按钮改为“需讲解”开关：应写开关显示、状态切换及本期实际变化的联动；原有学案 / 作业 Tab、答案展示、题卡排序、题干折叠均不提交。背景目标也只说明此次开关改造，不能先介绍整个页面的横屏布局和功能清单。用户没有提供背景原因时，可只写直接对应改造的目标，不编造痛点、指标或收益。

只有用户明确要求**完整 PRD**时使用 `mode: full`，并用 `fullRequest` 引用该授权原文。整页点击提示独立由 `hotspotMode: full` 与 `hotspotRequest` 控制；完整 PRD 不会自动开启整页提示。

## 内容放在哪里

| 内容 | 草稿字段 | 输出 |
| --- | --- | --- |
| 本期背景 / 问题，确有依据才写 | 可选 `document.background[]` | Markdown 需求背景 |
| 本期目标，确实需要说明才写 | 可选 `document.goals[]` | Markdown 需求目标 |
| 对应元素的具体改造规则 | `annotations[].items[]` | Markdown 序号标注 |
| 本期实际改变且需提示的具体交互 | `hotspots[]` | 短暂橙色点击提示 |

页面需求默认省略。background / goals 每条用 `{requirementId,text}` 写一个本期问题或目标，不写页面总览、旧业务清单、研发实现或多条拼成的段落。只有确需更新现存背景 / 目标时才提交并使用 `--replace-doc`，不能为了落库重复生成。

标注每条使用 `{section,requirementId,markdown}`。section 从下列内容中选择适用项，**可只写一项，不凑齐五项**：

| section | 本期内容 |
| --- | --- |
| 页面显示 | 本次相关状态下的显示差异、文案和可见性 |
| 数据流转 | 已知的输入输出、传递和更新时机；不编造接口 |
| 业务规则 | 本次相关计算、校验、条件、范围与约束 |
| 交互说明 | 本次相关触发、响应、跳转及必要联动 |
| 异常情况 | 本次相关错误、边界、失败反馈与恢复 |

每个 markdown 条目只包含一个顶层 `1.` / `-` 列表项，或同一需求的一张状态表；不同规则拆成不同 items，不在一个 item 塞多个顶层列表项。工具生成标题与空行，保存为普通 Markdown；不接受无逐条依据的整段 body，也不把需求 ID 显示到正文中。未改功能不要为了凑小节而写。未知接口、权限、阈值等放进 unknowns，并在回复中说明待确认，不自动落库。

## 草稿格式（版本 3）

写入项目 `.prototype/prd.draft.json`，UTF-8、合法 JSON。以下是“按钮改开关”的格式示例，应替换为本期真实需求和当前 revision：

```json
{
  "schemaVersion": 3,
  "baseRevision": 0,
  "scope": {
    "mode": "delta",
    "request": "将我不需讲解按钮改为需讲解开关，切换后即时生效。",
    "requirements": [{
      "id": "R1",
      "text": "将讲解意愿改为开关表达",
      "sourceQuote": "将我不需讲解按钮改为需讲解开关",
      "before": "题卡使用我不需讲解按钮",
      "after": "题卡使用需讲解开关"
    }],
    "exclusions": ["原有 Tab 切换", "原有题卡排序及答案展示"],
    "hotspotMode": "delta"
  },
  "pages": [{
    "file": "pad.html",
    "stateId": "default",
    "targets": [{"protoId": "explain-toggle", "requirementIds": ["R1"]}],
    "document": {
      "goals": [{"requirementId": "R1", "text": "统一通过开关表达是否需要讲解。"}]
    },
    "hotspotAction": "replace",
    "hotspots": ["explain-toggle"],
    "annotations": [{
      "protoId": "explain-toggle",
      "items": [
        {"section": "页面显示", "requirementId": "R1", "markdown": "- 使用需讲解开关表达当前讲解意愿。"},
        {"section": "交互说明", "requirementId": "R1", "markdown": "1. 切换开关后即时更新讲解意愿。"}
      ]
    }]
  }],
  "unknowns": []
}
```

- 工具元数据仍为版本 2，草稿是独立的版本 3。旧草稿应按本期需求重写，不能只改版本数字；工具不会自动迁移旧正文。
- `file` 为项目相对路径，也可用登记后的 pageId；同时提供时 file 优先。stateId 默认 default，须已登记。多端项目先读多端协议，默认只写业务 page，不把业务规则标到 launcher 演示壳上。
- 每个 target 使用 `requirementIds` 数组；元素内的每条标注只能引用该 target 绑定的需求。纯背景 / 目标更新可用页面级 `requirementIds`，不必为文档编造元素目标。
- 默认 create：已有绑定跳过。需要按本期规则重写既有未确认标注时用 `action: update`，保留标注 ID、序号和锚点；不要误以为重复 create 会替换旧正文。
- 用户手动删除的目标不补回；只有明确要求恢复某条才用 `action: restore`。已确认标注和文档保留。
- hotspots 单独列出具体控件 ID，须是 targets 子集；省略保留既有配置，新页缺省无提示；显式清单替换，[] 或 hotspotAction: clear 清空。只整理 PRD / 布局时不顺带改热点；新一轮交互改造必须显式提交本期清单（无提示也提交 []），避免沿用上期交互。容器标注、历史标注和 data-proto-id 不授权后代提示。
- 标注绑定隐藏区域时，先按接入约定为目标及其外层区域补齐 `data-proto-reveal-by` 显现路径，核对默认隐藏时有入口引导、点击右侧序号能自动展开。仅在正文写“点击设置后展示”不会建立运行时关联；不要用无关的“确定 / 清空”按钮作为入口，也不要扩大 hotspots 来代替展开路径。

## 精确点击提示与更新语义

页面级 `hotspotAction` 支持以下操作，兼容版本 3：

| 本次操作 | 草稿写法 | 保存结果 |
| --- | --- | --- |
| 只整理 PRD，保持提示 | 省略 hotspotAction 和 hotspots；或只写 `hotspotAction: "preserve"` | 保留该状态原值，新页仍无提示 |
| 替换为本期控件 | `hotspotAction: "replace"` 与 `hotspots: ["具体控件ID"]` | 精确替换，不和历史清单合并 |
| 明确关闭该状态提示 | `hotspotAction: "clear"` 或 `hotspots: []` | 保存空清单 |

preserve 与 hotspots 同时出现、replace 缺清单、clear 配非空清单会拒绝导入；scope.hotspotMode 的 full / off 分别要求 replace / clear，不能和页面操作冲突。full 仍须用户独立明确要求，完整 PRD 不会隐式开启整页提示。

绑定与验收：

1. 在实际按钮 / 开关上使用唯一稳定 ID；容器可以承载 PRD 锚点，热点不能复用其范围。委托到祖先的事件，在具体控件自身加 `data-proto-hotspot="true"`，同时验证真实操作，不能为了过校验把所有元素都标 true。
2. 导入拒绝包含其他控件的容器和被 false 排除的目标；缺失 / 重复 ID 默认阻止整份写入。--skip-missing 的部分跳过必须查看报告并说明，不能把漏掉当成功。
3. 报告 `hintActions` 说明保留 / 替换 / 清空，`hotspotChecks` 说明已声明或待运行时确认。`runtime-check` 不等于已验证可提示；HTML 解析不能证明 addEventListener、React 或事件代理的最终行为。
4. 在工作台相应页面 / 状态点击空白，核对橙色层只覆盖本期具体控件；在原型窗口调用只读 `ProtoHotspots.inspect()` 查看逐 ID 结果。ready 可提示；missing / duplicate / no-action / container / oversized 须修正；excluded 表示主动排除；hidden / disabled / offscreen / occluded 需进入实际可操作状态再验收。不要通过执行保存 / 删除等操作来试探热点。
5. 只修提示映射 / 声明时保留已有 PRD、序号与用户删除结果；不借修热点补全整页需求。工具升级不会自动改写既有原型文件和私有元数据。

工作台允许用户手动编辑热区。`interactionHints.manualTargets` 为手动添加，`excludedTargets` 为用户删除 / 排除；不要在落库脚本中重置这两层。工具 replace 基础热点时保留它们；明确 clear 会关闭手动添加，排除记录仍保留。手动添加不会授权整个容器或兄弟控件。

用户还可在标注更多菜单“关联展开入口”保存 `anchor.revealSteps`，用于手动指定多级 Tab / 分组等显现路径。保留该字段，不用重新生成的自动 conditions 覆盖用户路径；PRD update 只改正文。已确认标注仍受保护。路径修改只涉及显现关联，不代表用户授权补全 PRD 或执行保存 / 删除等业务动作。

## 重新整理时清理已误写的内容

重新落库不是清空所有 PRD 后重建。先核对现存内容：本期相关标注用 update 精简；已有背景 / 目标确需纠正时提交本期 document 并使用 --replace-doc；已确认内容、用户删除结果、其他时期和其他页面的历史需求保留。不要为了通过新格式而复制旧正文、自动扩大 scope 或重置 confirmed。

用户明确要求清理本期误写的无关标注时，可以在 scope.cleanupRequest 引用本次整理 / 清理授权原文（也包含在 scope.request 中），并在对应页面添加：

```json
"removals": [
  {"annotationId": "实际存在的标注ID", "reason": "该条只描述保持不变的原有功能，不属于本期改造。"}
]
```

只点名已核实的误注，不能整页删除或顺带清理无法确认来源的历史内容。工具按页面 / 状态和标注 ID 定位，保留已确认标注、记录删除定位，避免后来补回。同一标注不要同时删除和重建，改写用 update。无法确认归属或受 confirmed 保护时保留并报告具体条目。

## 执行、校验与回报

1. 先按前文完成具体范围确认，再完成实际需要的页面 / 状态登记，读取最新 revision 生成草稿。使用工具仓库中的 `python "<工具仓库>/proto_import.py" "<原型项目>" --dry-run` 检查，按已确认清单逐项比对后完成正式导入，不把 dry-run 当成已落库。
2. --dry-run 不保存 PRD / 点击提示或归档草稿，但可能创建元数据或补登记页面；revision 因登记改变时，重新读取并核对后生成草稿，不机械更新数字。--skip-missing 仅在用户接受部分导入时使用。
3. 工具校验需求引用、前后差异、逐条正文、元素定位、页面状态和基准 revision，生成 Markdown 与锚点；任何错误保留草稿，不写本次 PRD。确认保护、删除保护仍生效。实际变更才增加 revision，草稿归档到 `.prototype/imported/`。
4. 复核导入报告中的本期需求、改造差异、contentRefs、清理项、点击提示范围、跳过项与 unknowns。contentRefs 是提交内容的追溯表，实际保存结果以 documents / annotations / removedAnnotations / skipped 为准；工具校验不替代 Agent 的语义自审。
5. 成功后说明落在哪个项目、页面 / 状态，是否复用已有项目，并附报告的 viewerUrl；简述本期实际写入及清理了什么、明确未处理的保护项。默认链接来源为 http://localhost:8080，来源不同用 --viewer-origin。
6. 已有 PRD 不会因工具升级自动清理；也不因更新 skill 就表示已重新落库。非 0 退出如实报告；元数据冲突或未完成写入时保留现场，不用旧快照覆盖、不删除 .pending-write.json。首页登记另按接入约定完成。
