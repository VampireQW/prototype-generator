# 发布更新提示、版本对比与更新说明方案

日期：2026-11-03。状态：已实现；实际能力、协议和验证见功能文档、API 文档与 `docs/archive/task_20261103_release_updates.md`。以下保留评审时的设计依据。

落地范围：研发版更新提醒与说明、现有发布 / 导出统一、事实差异和可编辑草稿、跨页 / 状态 / 隐藏目标定位、Git 原子提交、旧基线引入、部署状态。当前固定保留 10 次轻量历史、当前与上一完整资源，不新增用户配置；纯净版不注入提醒 UI，更深入的 AI 语义总结留待后续。

目标：研发一直开着旧评审页面时，能明显得知新版本已上线；本地自动比较上次发布与当前内容，按页面生成简洁更新表，点击条目可以进入对应页面、状态和位置。

## 现有代码能复用什么

- `review_export.py` 已构建研发壳、PRD、序号、热区和导航，并为最终注入的原型 HTML 计算 `prototypeVersions`。现有 hash 解决的是重新加载时的 iframe 资源版本，尚无旧页面主动检查新发布的机制。
- `src/review_shell.html` 已有页面 / 状态切换、iframe 握手、序号选中、PRD 定位及 `reveal` 展开。更新条目的定位应复用这些能力，不能重新做一套屏幕坐标。
- `server.py:github_upload_dir` 仍按文件逐个 Contents API 提交；如果直接把版本文件加进这个循环，可能在其他资源尚未上传时就让旧页面检测到更新。
- `github_pages.py` 的取消发布已有 Git tree / commit / ref 更新能力，可以提取公共逻辑，为发布提供整批提交，而不另起发布系统。
- 手动文案编辑已有 `.prototype/text-edits/` 记录与 HTML 内嵌文本覆盖规则，可辅助识别具体控件的前后文案。

## 1. 用户看到的交互

### 已发布页面

在研发版顶部显示高对比、常驻的更新条：

> 页面有更新，请刷新查看最新版本。涉及 3 个页面、6 项变化。 [刷新页面] [查看更新] [稍后]

- 不自动刷新，不打断正在阅读的 PRD、弹窗或原型操作。
- “稍后”收为仍可见的“有更新”提示，不把更新状态彻底隐藏。
- 展示在壳的布局区域，不压住原型操作区；适配浅暗主题和窄屏。
- 当前页可见时约每 30 秒检查一次轻量版本清单，切回标签页时立即检查；隐藏标签页暂停，网络失败退避重试，不反复弹错误。
- 只读取同站点静态 JSON，不要求研发登录 GitHub，不把 Token 放到前端。
- “刷新页面”加载已检测到的版本，保留当前页面 / 状态；目标已删除则进入默认页面并说明。

首版重点覆盖研发版。纯净版若启用提示，需要为每个业务 HTML 注入轻量检测与提示，保留纯净版不带 PRD 的定位；可在后续扩展共用检测模块。单纯 file:// 打开的离线导出不轮询服务器，但研发包仍可查看随包携带的更新说明。

### 本地发布窗口

在现有首页发布浮窗和工作台发布区复用“更新说明”入口，默认比较**同一项目、同一发布目标的上次成功发布**。

- 自动生成“较上次发布：3 页、6 项更新”的摘要。
- 可查看差异表和修改说明文字，生成和普通发布不额外增加每次必填的确认步骤。
- 表格只列变化，不重新罗列整页功能，也不写回或扩写现有 PRD。
- 本地草稿定位到当前工作台；发布时把同一份说明带进研发交付包。

以下为交互示例，不代表当前项目的实际差异：

| 页面 / 状态 | 类型 | 更新内容 | 操作 |
| --- | --- | --- | --- |
| 班级对比 / 默认 | 文案 | “导出”改为“导出 Excel” | 定位按钮 |
| 答案设置 / 弹窗 | PRD | 补充“允许不填”的判分规则 | 定位标注 |
| 扫描详情 / 默认 | 页面 | 新增截图页面 | 打开页面 |
| 作业列表 / 默认 | 删除 | 移除旧筛选项 | 查看删除内容 |

PRD 文档变化与原型实现变化必须分类型：只改了说明，不能自动写成“功能已实现”。

## 2. 自动更新说明的生成规则

以规则提取和真实差异为底稿，不依赖 AI 凭空理解所有源码。可后续增加 AI 润色，但 AI 只能基于提取出的差异，不补造需求与未变化功能。

| 变化来源 | 自动生成的粒度 | 定位方式 |
| --- | --- | --- |
| 页面新增、删除、改名、移动、状态变化 | 每个页面 / 状态的结构变化 | pageId + stateId |
| PRD 与标注正文 | 按稳定文档 / 标注 ID，提取变动标题、条目或前后短句 | noteId 或文档段落 |
| 手动文案修改 | 对应控件的旧文案 → 新文案 | 稳定锚点 / 文本编辑语义键 |
| HTML 静态内容 | 能稳定匹配的按钮、表头、字段、内容块差异 | data-proto-id / id / 可验证语义锚点 |
| 热区、展开路径 | 新增、移除、目标或动作的变化 | 热区 / 标注所属页面和区域 |
| 截图替换 | 替换图片、尺寸变化；不猜图片内文字或业务意图 | 图片页；已有可验证区域时定位区域 |
| 公共 CSS / JS / 资源 | 合并为一条共享更新，列受影响页面 | 页面列表或明确关联区域 |
| 任意动态逻辑、无法语义匹配的源码 | 如实写“此页面交互代码有更新，需核对”，不编造功能结论 | 页面级定位，标出粒度 |
| 评审运行组件 | 单列“评审组件更新”，不当作业务需求变化 | 评审说明 |

忽略 revision、保存时间、发布时间、临时高亮、构建注入噪声及显示序号重排。标注 ID 稳定时，序号从 2 变成 1 不能被算成删除再新增。只调整锚点 / 落点可归类为“标注位置调整”，避免混为业务需求变更。

相同页面、状态、目标的多个相关变化应合并；没有依据的细分不做。新增页面默认概述为一条页面新增，不把全部元素分别列成新增功能。

## 3. 快照与第一次使用

本地新增独立的 `.prototype/releases/`，不改变现有 project / prd / changes 三文件协议。

- 保存项目 / 页面 / 状态、PRD、标注、相关源文件的规范化摘要、必要文本快照和资源 hash。
- 不默认复制整套图片、视频、vendor、旧产物、密钥、日志和项目外文件，避免刚清理完又制造大量重复资源。
- 发布目标至少区分 owner / repo / branch / remote project identity；项目改名继续沿用稳定项目身份。
- 本地导出不推进“上次发布”的基线；发布失败也不推进。
- 发布说明草稿绑定源内容指纹。生成后又修改项目，发布前重新计算并更新差异，防止发布过期说明。
- 从同一个冻结的构建副本计算差异和构建产物，防止一边编辑一边打包导致说明、PRD 与 HTML 不一致。
- 建议默认保留最近 10 个有内容变化的版本，数量可配置；当前和上一有效基线保留。无变化的重发不新增需求差异历史。

已有项目第一次启用时，优先从**已发布研发版**读取嵌入 PRD 与页面数据、原型内容，规范化为初始基线。两侧按同一种内容层比较，过滤评审脚本注入，避免把全部旧内容误报为新增。

远端只有纯净版、数据不足或网络不可达时，不伪造历史：显示“首次建立版本基线，历史差异暂不可完整比较”，保留已有记录，从本次成功发布后开始完整对比。没有发布记录的新项目显示首次发布摘要，而不是自动撰写全量 PRD。

## 4. 版本检测与发布一致性

每个已发布研发站点携带轻量 `prototype-release.json`，以及按发布 ID 命名的更新说明 JSON。命名空间必须检查冲突；不能静默覆盖源项目同名文件。

版本清单包含 schemaVersion、递增序号、releaseId、contentVersion、发布时间、输出类型、更新项统计及更新说明路径。发布时间继续与本地浮窗、产物页头、登记表共用本次发布的同一个值。

- releaseId 识别一次发布，contentVersion 识别实际内容，序号用于拒绝 CDN 回退的旧清单。
- contentVersion 覆盖原型、PRD、资源和评审运行组件，排除发布时间等波动字段。只重新部署、内容相同，不反复弹“有更新”。
- 累计落后多个版本时，可看到保留范围内各次更新；超出历史范围清楚提示，不把最近一次说明当成全部遗漏变化。
- 检测请求绕开浏览器旧缓存；刷新使用最新版本参数，并检查新清单 / 更新说明的 releaseId 一致。

缓存不能只处理壳 HTML。建议研发壳继续使用稳定的项目根入口，而原型文件放入按 contentVersion 区分的发布子目录；壳通过数据里的原型 base path 加载该版 HTML、CSS、JS 和图片。这样不必为了缓存去任意改写业务脚本，页面的相对资源也跟随版本切换。只保留当前与上一份完整原型产物，轻量说明保留最近 10 次；数量可配置。首次迁移保留旧 proto 路径的过渡副本，避免已打开旧页的资源突然失效；只清理发布器自己管理的版本目录，不触碰项目其他文件。

发布应改为：上传所需 blobs → 构造本项目新 tree（含清理本项目已删除旧产物）→ 创建一个 commit → 非强制更新分支 ref。这个 commit 同时包含原型、评审壳、版本清单和更新说明，其他项目保持原样。复用现有 Git tree 能力，远端 head 冲突时不强推覆盖别人的发布。

只有成功提交这批产物后才保存本地成功版本记录。还需区分“已提交 GitHub”和“站点已生效”：客户端以 Pages 实际可读到的新版本清单为准，不能在点击发布时就通知研发刷新。GitHub Pages 的提交与构建 / 部署是不同阶段，见 [GitHub 官方发布源说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)；tree / commit / 非强制 ref 操作依据 [Git tree API](https://docs.github.com/en/rest/git/trees) 与 [Git ref API](https://docs.github.com/en/rest/git/refs)。

实现时可将本地记录分为“已提交、等待站点生效”和“已验证生效”，分别记录，不让部署失败被误认为研发已经看到了新内容。当前草稿对比默认以上次成功提交的发布快照为基础，UI 明示其部署状态。

## 5. 点击更新后的定位

每个更新项保存结构化目标，而不是当前屏幕坐标：pageId、stateId、noteId（可选）、稳定元素锚点或截图相对区域（可选）。

执行顺序：切页面 → 等 iframe 握手 → 进入状态 → 按已有展开路径打开内容 → 滚到目标并高亮。必须等就绪信号，不靠固定延迟和重复点击。

- 标注变化复用现有 noteId / reveal。
- 非标注控件新增独立的变化定位消息，复用锚点与展开能力，不为更新条目自动创建序号或 PRD。
- 跨页面 / 状态的链接可携带定位信息，刷新后仍能执行。
- 旧版本页面查看最新说明时，操作显示“刷新并定位”，先加载对应版本，避免在旧 DOM 里定位新元素。
- 锚点不再可靠时退到所属页面并说明，不能假报定位成功。
- 已删除页面 / 元素无法在当前原型里高亮，操作改为“查看删除内容”，展示旧内容片段与删除说明。

## 6. 建议实现顺序

1. **发布与快照基础**：整批发布、版本清单、冻结内容快照、基线读取 / 保存和部署状态。这是后续提示可信的前提。
2. **可见更新提醒**：研发版轮询、明显提示、保留页面状态的刷新、异常退避和同内容重发去重。
3. **差异表与定位**：本地发布区入口、自动表格、可编辑说明、研发版随包展示及深链接定位。首版优先稳定支持页面、PRD / 标注、手动文案、截图和文件变化的诚实兜底；动态逻辑的业务语义润色后续扩展。

这三个步骤应作为一条完整交付链验收，不上线一个会提前提醒、但实际还没有完整新内容的中间版本。纯净版提示和更深入的 AI 总结在基础链路稳定后复用。

建议拆出独立版本 / 差异模块及共用更新说明 UI，不继续把逻辑大段堆进 server.py 和 viewer.html。复用已有项目权限、路径校验、发布错误分类和元数据冲突保护。

## 7. 验收范围

- A 版一直开着，B 版发布并生效后出现明显提示；后台标签页恢复时能发现。
- 发布失败、离线、404、部分网络失败和部署未生效，不误报有可刷新的新版本。
- 内容相同的重发不打扰；仅改 PRD、仅改截图、仅改运行组件均能正确处理。
- 远端逐批一致，其他项目不受影响；并发发布不强制覆盖。
- 三页只改一页，更新表只列事实差异；不把全量元素重新写成需求。
- 序号重排不制造假更新；共享资源变化不刷满重复记录。
- 修改说明后又改源码，发布时说明与冻结产物一致。
- 首次启用没有基线，不编造历史；有已发布研发版时能正确导入基线。
- 表格定位覆盖普通元素、标注、隐藏弹窗、Tab、截图和跨页面场景；删除 / 失效锚点有明确降级。
- 页面跨多次更新未刷新，能查看保留范围内遗漏更新并进入最新对应位置。
- 浅暗色、窄屏、离线研发包、现有序号拖动 / 编辑 / 高亮 / 展开和两种导出保持正常。

上线边界：机制上线前已经打开的旧页面不含检测代码，首次仍需手动刷新一次；浏览器被彻底挂起或没有网络时无法保证立刻收到通知。此后生效版本的检测以站点可读和标签页恢复为条件，不承诺即时推送。
